Cut from paper

Flat cutouts with hard outlines, in a crisp saturated storybook world, under a chunky party interface of the same family. The game and its menus finally come from one reference instead of two bolted together.

The outline is geometry, not a shader

This is the decision the rest hangs off. A character is a slab 0.08 m deep: coloured front and back, near-black on the four edge faces. That outlines the silhouette by construction — no inverted hull, no depth-buffer edge detection, no fullscreen pass, and no per-frame cost at all.

the edge you see when it turns is the outline

Slabs, not billboards — and that is a gameplay decision.

True camera-facing quads are the more authentic read, and they would remove depth judgement completely. In a game about timing a jump over a sweeping bar and dashing into a moving player, that is a playability risk rather than a stylistic one. The slab keeps the paper flip and keeps the cue.

Paper, generated in code

Every swatch below is produced in this page by the functions the spec defines — no image files, no loaders, so kit_check.py stays green by construction. Paper is a kinder subject for this than PS1 was: it wants flat colour, a whisper of fibre and hard lines, which are cheaper to write than to draw.

The generator kit · 64 × 64 · smooth · tiling

Eight faces, from four numbers

Inked linework on a cutout. faceFor(slot) varies eye spacing, eye size, brow angle and mouth shape from the slot seed, so the eight players get eight different faces — which one drawn texture could never do.

A player now carries three identity channels.

Colour, outline, and face. RD-007 found that eight simultaneously bright, saturated and dichromacy-safe colours is over-constrained, and named a second channel as the real fix without building one. This builds two.

The character

Every part is a slab: coloured faces, ink edges, hinged at the joints. Footprint and PLAYER_RADIUS are unchanged, so no collision, spawn or minigame geometry moves — this stays a render-layer change.

The interface, same construction

A panel is a character slab at UI scale: flat fill, a heavy ink outline, and a hard offset shadow with no blur. That shared construction is why the menus and the world now read as one thing.

Does generating assets in code perform better?

Asked directly, and the honest answer is no — not in any way that matters. Once a texture is on the GPU it is the same object whichever way its pixels arrived. Measured, rather than asserted:

Generated in codeShipped as filesWins
GPU cost per frameidenticalidenticaltie
GPU memoryidenticalidenticaltie
Cold start0 bytes, 0 requests, 8.5 ms CPU~26 KB, 16 requests, decodecode
Build & deploynothing to pipelineasset pipeline, cache-bustingcode
Artistic ceilingshapes and patternsanything at allfiles
So the rule is kept on its real grounds, not a borrowed one.

No asset files, because that makes the art loop which stalled the previous project structurally unavailable (RD-001). That is a process argument and a good one. Calling it a performance win would have been a rationalisation — and a constraint defended on a false basis is one that gets dropped the moment somebody checks.
